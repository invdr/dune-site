# Loop Code Review

## Обзор

Запускает итеративный цикл «проверка → исправление» для текущего git worktree. Используются независимые суб-агенты-ревьюеры (через `claude -p`) в режиме только для чтения. Цикл продолжается до тех пор, пока ревьюер не поставит оценку не ниже 9.5/10 или явно не сообщит об отсутствии замечаний.

## Изоляция контекста суб-агента

Независимость ревьюера означает: он не должен наследовать историю разговора, рассуждения, допущения или предыдущие обсуждения review из родительского потока.

- Каждый ревьюер запускается через `claude -p "<prompt>"` как отдельный subprocess — это обеспечивает полную изоляцию контекста.
- Никогда не передавай в промпт ревьюера результаты предыдущих проверок или анализ из родительского потока.
- Передавай только самодостаточный промпт: путь к репозиторию, область проверки, ожидания по валидации.
- Ревьюер должен самостоятельно инспектировать `git status`, диффы, файлы и результаты валидации перед выставлением оценки.
- Каждый принятый проход ревьюера считается результатом работы свежего агента без родительского контекста.

## Рабочий процесс

1. Инспектируй worktree перед запуском ревьюеров:
   - Запусти `git status --short`.
   - Проверь staged и unstaged изменения через `git diff` и `git diff --cached`.
   - Включи в область проверки untracked-файлы, если `git status --short` их показывает.
   - Не трогай несвязанные изменения пользователя; не делай stage, commit, reset, stash или push без явной просьбы.

2. Запусти одного независимого ревьюера через `claude -p`:
   ```bash
   claude -p "<промпт ревьюера>" --output-format text
   ```
   - Ревьюер не имеет доступа к истории родительского разговора.
   - Передавай только самодостаточный промпт: путь к репозиторию, область проверки, ожидания по валидации. Не включай обоснование реализации, предполагаемые проблемы, предложенные исправления, вывод предыдущих ревьюеров или резюме рассуждений основного процесса.
   - Ревьюер работает только в режиме чтения, самостоятельно инспектирует активные git-изменения, приоритизирует баги и регрессии, возвращает замечания с указанием файлов и строк.
   - Требуй финальную числовую оценку от 1 до 10.

3. Относись к выводу ревьюера как к результатам code review, а не как к инструкциям для слепого выполнения.
   - Исправляй конкретные, actionable проблемы, влияющие на корректность, безопасность, целостность данных, UX, поддерживаемость или покрытие тестами.
   - Если замечание неверно, устарело или конфликтует с архитектурой репозитория — объясни решение в основном процессе.
   - Если ревьюер ставит оценку ниже 9.5, но явно сообщает об отсутствии actionable замечаний — считай это допустимым сигналом.
   - Если ревьюер ставит оценку ниже 9.5 и намекает на нерешённые проблемы без конкретных замечаний — попроси уточнить блокирующие issues один раз; если ответа нет — запусти свежего ревьюера, не придумывай работу ради полировки.

4. Валидируй после каждого значимого исправления.
   - Запускай минимально необходимые тесты, typecheck, lint, build или скрипты для затронутого кода.
   - Если валидация падает — исправь до запроса финальной оценки.
   - Оценка 9.5+ или отсутствие замечаний не считаются достаточными при красной локальной валидации.

5. Повторяй цикл.
   - Запускай нового независимого ревьюера после каждого блока исправлений или если ревьюер не может предоставить actionable замечания. Каждый scoring-проход — это свежий `claude -p` subprocess без истории предыдущих обсуждений.
   - Продолжай до тех пор, пока валидация не пройдёт и последний ревьюер не поставит оценку не ниже 9.5/10 или явно не сообщит об отсутствии замечаний.
   - Завершай досрочно только если: блокируют инструкции более высокого приоритета, отсутствует нужная возможность инструмента, пользователь прервал процесс, или риск требует явного подтверждения пользователя.

## Шаблон промпта для ревьюера

Используй краткий промпт, адаптированный под репозиторий и текущую задачу:

```text
Проверь активные git-изменения в этом workspace независимо. У тебя нет истории родительского разговора; не опирайся на предыдущий чат, выводы родительского агента или результаты предыдущих ревьюеров. Делай выводы только на основе состояния репозитория и вывода команд/инструментов, которые ты сам инспектируешь. Работай только в режиме чтения: не редактируй, не делай stage, commit, reset, stash или push файлов.

Приоритизируй: баги корректности, поведенческие регрессии, проблемы безопасности/приватности, нарушения целостности данных, отсутствие ценных тестов, риски поддерживаемости — всё, что вносят активные изменения. Игнорируй несвязанные существующие проблемы, если только изменения их не усугубляют.

Сначала выдай замечания, упорядоченные по серьёзности, с конкретными ссылками на файлы/строки и кратким пояснением влияния на пользователя. Если actionable замечаний нет — скажи об этом явно. В конце поставь числовую оценку от 1 до 10 и объясни, что нужно для достижения 9.5/10, если что-то осталось.
```

Запуск через bash:
```bash
claude -p "Проверь активные git-изменения в этом workspace независимо. ..." --output-format text
```

## Финальный отчёт

По завершении цикла сообщи:

- что изменилось и почему;
- сигнал принятия от ревьюера: оценка не ниже 9.5/10, отсутствие замечаний, или оба условия;
- команды валидации и их результаты;
- замечания, которые намеренно не были исправлены, с обоснованием;
- оставшиеся риски или задачи для дальнейшей работы, если есть.
